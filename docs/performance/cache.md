# 商户缓存治理对照

## 问题与基线

2026-09-17，在基础业务完成后测量 Cache Aside V1。命令：

```powershell
docker compose -f docker-compose.test.yml run --rm --no-deps test go test ./tests/integration -run TestShopCacheComparisonEvidence -count=1 -v
```

环境为独立 MySQL 8.4 / Redis 7.4、Go 1.26.4 Linux 容器。数据库访问次数在真实 Repository 外计数；并发冷查询人为加入 50 ms 回源延迟，以复现请求重叠。这是负载放大对照，不是延迟或吞吐 Benchmark。

| 场景 | V1 冻结参考 | 修改前运行实现 |
| --- | ---: | ---: |
| 同一不存在 ID 连续查询 100 次 | 100 次 DB 读取 | 100 次 DB 读取 |
| 同一未缓存 ID 并发查询 64 次 | 64 次 DB 读取 | 64 次 DB 读取 |
| 已缓存 ID 连续查询 100 次 | 0 次 DB 读取 | 0 次 DB 读取 |

测试保留独立命名空间中的 V1 参考实现：GET → SELECT → 固定 30 分钟 SET。数据使用本次测试独有的商户 ID，测试后清理。

## 预期变化

为不存在记录增加短期空值缓存，按商户 ID 合并并发回源；正缓存加入随机刷新时间和硬过期时间，逻辑过期后先返回旧值，再异步重建。后台任务需要超时、并发上限、失败退避和明确的关闭过程。

目标是在单进程中将重复空查询和同一 ID 的重叠回源合并到一次数据库读取，同时保持暖缓存零回源。逻辑过期允许短期旧值，不能宣称强一致。

## 优化后实测（2026-09-17）

使用上面的同一测试命令、样本和计数方式：

| 场景 | V1 冻结参考 | 当前实现 |
| --- | ---: | ---: |
| 同一不存在 ID 连续查询 100 次 | 100 次 DB 读取 | 1 次 DB 读取 |
| 同一未缓存 ID 并发查询 64 次 | 64 次 DB 读取 | 1 次 DB 读取 |
| 已缓存 ID 连续查询 100 次 | 0 次 DB 读取 | 0 次 DB 读取 |

当前实现的 1/1/0 结果已成为测试断言。真实 Redis 测试另验证 100 次逻辑过期读取立即返回旧值，仅启动一次受控回源，完成后读到新值；这证明指定单进程场景下回源次数减少，不代表整体吞吐提高。

## 暖缓存 Benchmark

环境：Go 1.26.4 Linux amd64 容器，Redis 7.4，同一 Docker Compose 网络，主机 AMD Ryzen 5 9600X，Go 报告 12 个逻辑 CPU；未设置独立 CPU 配额，主机负载与容器调度会影响结果。顺序调用 Service 详情方法，预热和测试数据准备不计时；包含 Redis I/O 与 JSON 处理，不包含 HTTP、鉴权或生产网络。

## 取舍与限制

- 同进程按 ID 合并，跨实例仍可能各自回源；最多 64 个不同 ID 在途，不等同于全局速率限制。
- 逻辑过期允许最多 5 分钟旧值窗口，失败退避不延长硬过期；正缓存初始硬 TTL 为 35–40 分钟。Redis 不可用时不能保存共享退避。
- CAS 只保护基于重建快照的发布，不能解决空 key 的更新竞争或取消已被读到的旧值；详见 [缓存一致性边界](../api/shop.md#缓存一致性边界)。
- 空值记录和缓存元数据消耗额外 Redis 内存，逻辑过期重建还包含一次二次读取；随机 ID 大量进入仍会增加数据库负担。
- 当前对照没有模拟多实例、长时间 Redis 故障或生产流量分布，专用指标与整体负载验收仍待后续阶段完成。
