# 秒杀 HTTP 负载基线

## 问题与验证目标

Seckill V1 在同一活动行锁上串行完成资格检查、重复检查、扣库存和插单。请求要等到提交后才收到成功；重复购买和售罄请求也进入事务。先建立可重复的 HTTP 对照，再实现 Redis Lua + Stream 入口，评估受理耗时与落库耗时的变化。

本报告记录 2026-09-17 的 V1 测量。完整 V2 尚未实现，仅增加了内部 Lua 受理原语，没有异步化性能提升声明。原始 18 组结果见 [JSON Lines](seckill-v1-baseline.jsonl)，相关源文件的 SHA-256 见 [测量时文件摘要](seckill-v1-sources.json)。测量时工作树包含未提交实现，不能用旧 Git HEAD 代替本次代码版本；摘要对应当时文件的原始字节，换行转换也会改变摘要。

## 可复跑命令

```powershell
docker compose -f docker-compose.test.yml up -d --wait
docker compose -f docker-compose.test.yml run --rm --no-deps -e RUN_LOAD=1 test go test ./tests/integration -run '^TestOrderHTTPLoadBaseline$' -count=3 -v
docker compose -f docker-compose.test.yml down
```

只作用于独立 `locallife_test` 数据库和测试 Redis；`RUN_INTEGRATION=1` 由测试 Compose 注入，负载另需显式 `RUN_LOAD=1`。普通测试和 Race 不会默认执行负载。每个子场景创建独有用户、商户、活动、Session，完成后停止 HTTP、删除自己的订单与样本，不清空数据库或 Redis。Redis Session 在计时前创建，验证码与登录耗时不计入基线。

测试明确装配 `service.NewOrder` 事务实现，后续异步 HTTP 路径应使用独立对照，不允许悄悄替换 V1 基线。

## 环境与测量口径

| 项目 | 本次配置 |
| --- | --- |
| Docker Engine | 29.7.2，Windows Docker Desktop 的 Linux 容器 |
| Go | 1.26.4，linux/amd64，12 个可见逻辑 CPU，未启用 Race |
| MySQL | 8.4.11，测试数据目录 tmpfs，最大连接 20、空闲连接 10 |
| Redis | 7.4.11，连接池 10，测试实例不持久化 |
| HTTP | Hertz 真实 TCP 回环监听，真实路由/超时/鉴权/事务，客户端与服务在同一个 Go 进程 |
| 超时 | HTTP 3 秒，依赖默认 2 秒，负载客户端 5 秒 |
| 日志 | 结构化请求日志经 JSON Handler 写入 `io.Discard`，不含终端日志输出的 I/O 成本 |
| 预热 | 每个场景先执行 20 次已鉴权订单列表查询，不改变活动库存 |

每组使用固定数量 worker 闭环发送，前一请求完成后才发下一请求。HTTP Keep-Alive 开启，连接上限等于并发数。计时从释放 worker 到全部请求读完响应；不包含数据准备、预热、核对和清理。初次创建购买连接以及请求编码、响应读取解析成本包含在测量中。

准备与负载使用独立期限：预热完成后才开始 30 秒负载预算，取消后停止领取新任务；全部 worker 返回后排空 HTTP，再使用新的 5 秒预算核验数据库。`planned_requests` 是计划数量，`requests` 是已发起尝试数量，`not_dispatched` 是未领取数量。取消边界上已经领取的少量尝试可能在 HTTP 客户端中失败，因此它们不等于确认到达服务端的流量。每批先输出 `LOAD_HTTP_RESULT`，即使后续数据库核验失败也保留 HTTP 统计；完整核验输出 `LOAD_RESULT`，未派发或错误会导致测试失败。本次公开样本均完整派发并成功完成核验。

- `QPS = 完成请求数 / 批次耗时`，包含成功和拒绝响应；不是每秒成功落库订单数。
- P95/P99 采用 nearest-rank，覆盖所有请求，包含业务拒绝和系统失败；统计函数有固定样本测试。
- `system_error_rate`：传输失败、无效响应、非预期状态及 5xx 占比。
- `non_success_rate`：全部非成功占比，包括预期的 409 业务拒绝。售罄与重复购买分别计数。
- `accepted`：验证响应用户、券、订单 ID、状态后的 HTTP 200 数。V1 成功表示事务已提交，必须与最终 MySQL 订单逐一匹配。
- `db_pool_waits / db_pool_wait_ms`：计时窗口内 `database/sql.Stats` 的等待次数与累计等待时长差值；多个请求同时等待，累计值可以超过批次墙钟时间。它不是 MySQL 行锁等待时长。

## 工作负载

每个组合独立执行三轮，并发为 1、16、64。

| 场景 | 独立用户 | 请求数 | 初始库存 | 预期结果 |
| --- | ---: | ---: | ---: | --- |
| purchase：库存充足 | 300 | 300，每人一次 | 300 | 300 成功，最终 300 单、库存 0 |
| oversubscribed：超额抢购 | 200 | 400，每人两次 | 100 | 100 成功、100 重复、200 售罄，最终 100 单、库存 0 |

超额场景按用户序列分两遍提交，worker 调度可能使两遍在边界重叠，并不保证每个用户的两个请求同时抵达。测试拒绝把同一订单的两次成功响应计为两次有效受理，并逐项验证唯一用户、响应订单和数据库记录一致。

## V1 实测

下表为每组独立三轮的最小–最大值，不对不同轮次的百分位再取平均。毫秒保留两位小数，完整精度与每轮样本保留在原始 JSON Lines 中。

| 场景 | 并发 | 批次 QPS | P95 (ms) | P99 (ms) | 每轮受理 / 最终订单 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 库存充足 | 1 | 269.60–297.50 | 3.98–5.50 | 4.23–8.45 | 300 / 300 |
| 库存充足 | 16 | 421.96–458.67 | 35.91–42.14 | 36.75–43.24 | 300 / 300 |
| 库存充足 | 64 | 408.71–447.45 | 272.83–305.46 | 343.85–421.38 | 300 / 300 |
| 超额抢购 | 1 | 348.00–357.08 | 3.84–4.19 | 4.40–4.91 | 100 / 100 |
| 超额抢购 | 16 | 617.45–639.00 | 34.78–37.60 | 35.65–38.84 | 100 / 100 |
| 超额抢购 | 64 | 531.37–638.73 | 221.45–271.22 | 313.41–376.99 | 100 / 100 |

18 组共 6300 次请求、3600 个已提交订单，均满足：最终库存 0、无超卖、无重复用户订单、HTTP 成功与订单逐一对应、系统错误率 0%。库存充足场景非成功率为 0%；超额场景非成功率为 75%，均为预期的重复购买与售罄。

并发 1/16 时没有数据库连接池等待；并发 64 时，库存充足每轮出现 279–280 次等待，累计约 25.1–27.2 秒，超额场景每轮 380 次等待、累计约 24.7–29.3 秒。库存充足从 16 增至 64 并发没有明显增加批次吞吐，却显著增加尾延迟；这一现象与同活动串行事务的设计相符。尚未单独采集行锁等待时长，不能把全部耗时归因于行锁。

## 后续改动与预期

在资格受理阶段由 Redis Lua 原子校验活动、库存和重复购买，扣减暂态库存、记录购买标记并 XADD。HTTP 返回明确的异步受理状态，消费者再通过 MySQL 事务形成最终订单。预期减少入口重复/售罄请求对 MySQL 的访问，将数据库提交等待从受理响应中分离；数据库仍是最终事实来源，消费速率与积压必须单独观测。

V2 对照需要保留相同并发、用户、库存与数据库连接配置，并同时记录：受理 QPS/P95/P99、最终订单数、库存一致性、积压清空时间与受理到落库耗时。不能把 V2 的“已接收”响应直接当作比 V1“已提交”更快的订单创建，也不能忽略消费者停机和恢复期间的积压。

异步化额外带来跨 Redis/MySQL 的一致性责任：重复消费幂等、处理后 ACK、Pending 接管、限次重试、失败记录、补偿、响应丢失后的状态查询、退出排空。仅有 Lua 扣库存加一个消费者循环不足以交付 V2，故障测试与恢复流程属于实现范围。

## 限制

这是每批约 0.63–1.15 秒的短时、闭环、单进程实验，没有模拟持续开放到达流量。排队在 worker 派发前的等待不计入单请求延迟，因此存在闭环负载的协调遗漏；它适合受控版本对照，不能确定可持续生产容量。

客户端与服务共享 CPU，MySQL 在 tmpfs、Redis 未持久化，依赖使用容器网络，日志没有终端输出成本。结果不包含生产磁盘持久化、跨主机网络、多实例流量分布或长时间运行的影响。后续工程验收仍需补持续负载、故障恢复、指标和 V2 实测。

## Lua 受理路径基线

内部原语实现后，在同一 Go 1.26.4 / Redis 7.4.11 Linux 容器环境执行：

```powershell
docker compose -f docker-compose.test.yml run --rm --no-deps test go test ./tests/integration -run '^$' -bench '^BenchmarkSeckillLuaAdmission$' -benchtime=1s -count=3 -benchmem
```

每轮先准备独立活动并预热一次脚本，然后以不同用户连续受理；计时包含 Lua、Redis 网络、事件写入和 Go 响应解析，不包含初始化和预热。结束后核对 Stream 条数等于计时请求数加预热事件数、库存为 0。没有模拟 HTTP、Session、消费者或 MySQL 落库。

| 轮次 | 次数 | ns/op | B/op | allocs/op |
| --- | ---: | ---: | ---: | ---: |
| 1 | 5988 | 216131 | 768 | 27 |
| 2 | 6006 | 236453 | 768 | 27 |
| 3 | 4764 | 240711 | 768 | 27 |

主机 AMD Ryzen 5 9600X，12 个可见逻辑 CPU，未开启 Race。原始输出见 [Lua Benchmark](seckill-lua-baseline.txt)。约 216–241 微秒/次仅作为内部受理路径回归基线；与上面的 HTTP 提交路径范围不同，不能直接计算吞吐提升或订单落库加速比例。完整异步链路仍需消费、恢复与最终一致性验收。
