# 商户查询接口

基础路径：`/api/v1`。三个接口均可公开读取，无需登录。响应使用统一的 `code/message/data/request_id` 结构，ID 和分类 ID 均编码为字符串，避免 JavaScript 大整数精度丢失。

## 商户分类

`GET /shop-types`

返回全部分类，按 `sort_order ASC, id ASC` 排序。成功的 `data`：

```json
[{"id":"1","name":"示例·餐饮","icon":""}]
```

## 商户列表

`GET /shops?type_id=1&page=1&page_size=10`

| 参数 | 默认值 | 约束 |
| --- | --- | --- |
| type_id | 不筛选分类 | 若提供，必须为正整数，最大为 uint64 |
| page | 1 | 1–1000 |
| page_size | 10 | 1–50 |

已知参数的显式空值、重复值、负数、小数或越界值返回 400。未知查询参数被忽略。列表按商户 `id ASC` 排序；从 MySQL 多查一条判断 `has_more`，不查询总数。

成功的 `data`：

```json
{
  "items": [{
    "id":"1",
    "type_id":"1",
    "name":"示例·街角面馆",
    "address":"上海市示例路 1 号（虚构商户）",
    "longitude":121.4737012,
    "latitude":31.2304001
  }],
  "page":1,
  "page_size":10,
  "has_more":false
}
```

分类不存在或当前页无结果时，`items` 为 `[]`。此版本采用 offset 分页，限制查询深度；并发增删时不提供快照一致性，也不用于附近商户的距离分页。

## 商户详情

`GET /shops/:id`

`id` 必须是 uint64 范围内的正整数。成功的 `data` 与列表中单个商户的结构一致。不存在时返回 404。

详情使用 `locallife:shop:v2:<id>`，记录商户值、逻辑刷新时间和硬过期时间。旧 V1 key 不再读取，按原 TTL 自然过期。

| 情况 | 行为 |
| --- | --- |
| 正缓存尚未逻辑过期 | 直接返回，读取不续期 |
| 正缓存逻辑过期、未硬过期 | 返回旧值并尝试后台刷新，同进程同 ID 合并为一个任务 |
| 空值缓存未过期 | 返回 404，不读取 MySQL |
| 未命中、硬过期、损坏或 Redis 读取失败 | 等待共享重建任务查询 MySQL；硬过期的旧值不再返回 |

正缓存的逻辑刷新时间为回填后 30–35 分钟，硬过期比逻辑刷新晚 5 分钟，因此初始 Redis TTL 为 35–40 分钟。不存在的商户缓存 30–45 秒；数据库故障不会被缓存成不存在。后台刷新失败（包括查询超时）会尽力延后 5 秒再试，但不延长原硬过期时间；Redis 不可用时无法保存这次退避。

每个服务实例最多同时重建 64 个不同商户，同 ID 请求加入已有任务。达到上限时，已有可读旧值仍返回，新的冷查询返回 429。单次缓存 GET、CAS 和维护 DEL 有 100ms context 预算；共享重建有 2 秒预算，失败退避另有最多 100ms 缓存写入预算。这些时间依赖底层 I/O 遵守 context，不是请求耗时的硬实时保证。

请求取消或超时只停止自己的等待，不取消其他请求共享的任务。服务关闭时取消并等待任务，然后关闭连接池。缓存回填失败不丢弃已查到的 MySQL 结果。应用启动与 `/readyz` 仍要求 Redis 可用，因为认证依赖 Redis。分类与列表直接查询 MySQL；专用缓存指标留待工程验收阶段。

## 商户维护

加载应用配置后，用实际商户 ID 执行：

```powershell
go run ./cmd/shop-update -id 1 -name "示例·新名称" -address "示例路 2 号"
```

至少提供名称或地址之一，省略字段保持原值。名称去首尾空白后为 1–128 个字符，地址最多 512 个字符，`-address=` 可清空地址；均要求合法 UTF-8。命令仅修改名称和地址，不改变分类或坐标，无需重建 GEO。

命令先在 MySQL 事务中更新和读取结果，提交成功后删除详情缓存。数据库失败不删除缓存；删除失败时命令非零退出，并明确提示数据库已提交，Redis 恢复后重试相同编辑可再次失效缓存。它是持有数据库配置的本地维护命令，尚无公开商户管理 HTTP 接口。

## 缓存一致性边界

MySQL 是权威数据源，缓存提供最终一致性。重建任务在查询 MySQL 前再次读取 Redis，并把这次读取的原始内容作为 CAS token：若这次观察到的非空记录随后被删除或替换，Lua 拒绝覆盖当前 key。

CAS 只保护缓存发布，不保证读取线性一致。删除后到来的冷请求仍可能加入删除前的在途任务并收到旧行，即使该任务写回缓存被拒绝。重建的第二次 GET 未命中或失败时使用空 token；即使最初请求见过正缓存，也属于空 token 情形。空 key → 数据库更新并 DEL → 仍为空 key 的竞争无法被该 CAS 识别，旧行可能被回填，受本次回填的硬 TTL 约束。

本地 singleflight 不跨进程；多个实例可能各自回源。直接执行 SQL 不会触发失效，删除失败也需要维护者重试。当前不实现分布式重建锁、延迟双删或 CDC；这些代价与证据见 [ADR 004](../adr/004-shop-cache-aside-v1.md) 和 [缓存对照](../performance/cache.md)。

## 错误响应

| HTTP | code | 含义 |
| --- | --- | --- |
| 400 | validation | ID 或分页参数无效 |
| 404 | not_found | 商户不存在 |
| 408 | request_canceled | 请求已取消 |
| 429 | rate_limited | 不同商户的并发重建任务达到上限 |
| 503 | dependency_failure | MySQL 查询失败 |
| 504 | timeout | 请求超时 |

启动和示例数据见 [本地运行](../quickstart.md)。
