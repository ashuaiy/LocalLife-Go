# ADR 005：Push Feed 与短期快照游标

- 状态：已采用
- 日期：2026-09-17

## Context

基础业务需要读取关注作者发布的内容。SPEC 要求 Push Model、`max score + equal-score offset` 分页，并验证同分场景不重复、不漏读。MySQL 保存内容和关注关系，Redis 保存可重建的有序索引。

直接在持续变动的 ZSET 上使用同分 offset 会出现位置漂移：第一页后若有同分成员迟到插入，或已消费成员被删除，后续 offset 可能重复或跳过原有内容。仅靠时间上界无法排除同一毫秒内迟到的推送。

## Decision

1. 内容保存到 MySQL 后，同步查询发布时间已存在的关注关系，按每批 500 个读者向 Redis ZSET 执行 `ZADD NX`。使用内容 ID 为 member、创建时间 Unix 毫秒为 score。
2. 第一次读取通过 Lua 原子复制当前读者的 live ZSET，记录条目数，并为快照和元数据设置固定 5 分钟 TTL。
3. 后续游标携带快照 ID、max 和 offset；使用固定集合上的同分 offset 累积算法。游标只在登录用户的 key 命名空间读取。
4. 每页以 Redis 事务读取条目数、元数据与候选，快照缺失或条目数不一致返回 409，要求客户端刷新。
5. MySQL 批量回填内容，并按当前关注关系与关注时间过滤。推进游标时使用原始候选数量，不依赖过滤后的数量。
6. 提供单用户 Feed 重建命令。暂停发布和关注变更后，从 MySQL 构建临时索引，校验完整条目数再原子替换 live；重建不修改已创建的分页快照。

## Alternatives / Why not alternatives

| 方案 | 当前取舍 |
| --- | --- |
| 直接在可变 live ZSET 上使用 max/offset | 同分迟到或删除导致位置漂移，无法满足分页测试要求 |
| 只按时间窗口冻结 max | 能排除较新的 score，不能排除相同或更早 score 的迟到推送 |
| 每次读取通过 MySQL 关联查询拉取 | 可以实现独立的 keyset 方案，但不符合当前已确定的 Push Model；后续按读写负载评估 |
| 改成复合排序键、序号或持久化分页版本 | 可以提供不同分页契约，会扩大当前索引与游标设计范围 |
| 引入消息队列和持久化投递任务 | 能改善推送失败恢复，但增加消费者、任务状态和重试职责；当前先提供明确失败语义与受控重建 |

## Consequences

- 固定候选集合使同分滚动分页可验证。刷新首页是新内容进入视图的明确边界。
- 首屏需复制完整 Feed，时间和空间成本随 Feed 大小增长；同一用户多个首屏请求会生成多个短期副本。live 当前没有保留条数上限。此决定优先保证基础版本正确性，不代表性能优化。
- 快照只固定成员及顺序，内容、点赞和关注状态仍实时读取。过滤后允许空页，调用方必须遵守 `has_more`。
- 内容写入和推送不是原子事务。推送失败不会回滚已发布内容，可能存在部分投递；当前依赖受控重建恢复，不宣称自动重试或 exactly-once。
- 重建只保证 Redis 发布的原子性，不保证与并发 MySQL 写入共同构成快照；操作期间必须暂停相关写入。
- 当前按所有关注者同步扇出，大量关注者会增加发布延迟；尚无大规模吞吐或内存收益的测量结论。

## When to revisit

在基础业务闭环完成后的 Benchmark 阶段，测量 Feed 条目数、并发读者、首屏延迟、续页延迟、Redis 内存和发布扇出成本。若已记录的负载超出预算，再评估保留窗口、索引版本、Pull/混合模式或持久化投递恢复，先保留当前正确性回归用例。

## Validation

- 真实 MySQL/Redis：16 个并发重复关注只产生一条关系，重复推送不增加成员数。
- 9 条内容中 7 条时间相同，跨多页读取；首页后插入同分迟到内容并重建，旧快照仍恰好读取原 9 条，新首页读取 10 条。
- 验证跨用户游标、快照丢失、固定 TTL、取消/重新关注过滤，以及过滤后仍正确推进游标。
- Redis 故障时发布返回失败但保留 MySQL 内容；重建恢复正确的内容 ID/score，失败的重建保留旧 live。
- 实际 HTTP 与 CLI 联调、全量单元测试、vet、build 和带真实依赖的 Race 检查通过，详见 [测试记录](../testing.md)。
