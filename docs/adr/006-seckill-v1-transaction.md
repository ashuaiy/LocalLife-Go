# ADR 006：Seckill V1 的 MySQL 事务下单

- 状态：已采用
- 日期：2026-09-17

## Context

基础业务闭环要求在并发抢购中保证不超卖、每位用户对同一张券只生成一笔订单，以及库存扣减与订单写入原子提交。现有 MySQL 表已具备非负库存约束和订单唯一约束；V1 先实现直接事务下单，后续再用数据评估异步化。

## Decision

Service 定义事务端口并编排业务规则。Repository 用 GORM 提供 `READ COMMITTED` 事务、SQL 操作及错误转换，提交或回滚仍由事务执行器负责；Handler 不直接操作数据库。

事务内先用 `SELECT ... FOR UPDATE` 锁定活动行，再读取数据库 UTC 毫秒时钟判断 `[begin_time, end_time)`。随后查询重复订单，条件扣减库存，插入订单并提交。活动行锁使同一券的资格判断和库存变更按顺序执行；RC 确保等待前一事务结束后能读到其已提交订单，也避免为不存在订单建立不必要的范围锁。不同券不共享应用级互斥锁。

`stock > 0` 条件更新与影响行数是库存检查的必要条件；`UNIQUE(user_id, voucher_id)` 始终作为最终兜底。即使另一个写入路径绕过重复检查，重复订单错误也会让本事务的库存扣减回滚。所有数据库操作传递请求 context。

创建、详情与列表均要求登录，仓储查询绑定当前用户；其他用户的订单与不存在的订单统一 404。资格失败使用不同的 409 业务码。

## Alternatives / Why not alternatives

| 方案 | 当前取舍 |
| --- | --- |
| 仅靠普通 SELECT 检查库存再 UPDATE | 检查与修改存在竞态，无法保护库存；必须使用条件更新 |
| 仅检查重复订单，无唯一约束 | 并发请求可能同时通过检查，数据库唯一约束不可省略 |
| 在 HTTP 层或进程内加互斥锁 | 无法保护多个服务实例或其他数据库写入路径 |
| 先在事务外校验活动时间 | 等待数据库锁期间可能越过结束时间，因此在取得锁后重新校验 |
| 使用默认 RR 并在不存在订单上做锁定读 | 会增加范围锁复杂度；V1 已按活动主键锁定并依赖订单唯一约束，采用明确的 RC 边界 |
| Redis 扣库存后直接写 MySQL | 两个系统没有原子提交关系，失败后需投递、幂等与恢复机制；交由 Seckill V2 阶段单独实现 |

## Consequences

- 单次事务包含活动锁、时间读取、重复检查、扣库存和插单，成功响应代表事务已提交。
- 热门活动在一行库存上串行化，会出现锁等待；没有宣称高吞吐，后续先记录 HTTP 负载基线，再比较 Lua/Stream 入口。
- 时间资格判断发生在取得锁之后；提交时间可以晚于活动结束，不能把提交时刻当作资格判断时刻。
- 唯一、外键、取消与插单故障都能回滚库存；自增订单 ID 可能有空洞，不应依赖连续 ID。
- 提交确认失败可能留下“客户端未收到成功、数据库已提交”的不确定结果。提供按券查询本人订单的恢复路径，不自动重试，不宣称跨网络 exactly-once。
- 当前状态只有“订单已创建”，没有支付、取消或退款；与后续异步入口的受理状态需要明确区分。

## When to revisit

完成基础闭环后，以固定库存、用户数和并发度记录 QPS、P95、P99、业务拒绝和系统错误，再引入 Redis Lua + Stream。保留当前事务作为最终落库的一致性基础，补充消费者幂等、Pending 恢复、失败记录和补偿验证。

2026-09-17 已完成 [HTTP 基线](../performance/seckill.md)：三档并发、两种负载各执行三轮，共 6300 次请求；无系统错误和库存/订单不一致。库存充足从 16 到 64 并发的批次吞吐大致持平，但尾延迟与连接池等待增加。下一步实施异步受理，并分别衡量受理响应和最终落库，不能混用两种成功语义。

## Validation

- 40 个用户同时提交 80 次请求，初始库存 15：成功 15、重复购买 15、售罄 50；最终库存 0、订单 15、不同购买用户 15。
- 外键插单失败，以及绕过业务检查后触发唯一约束的插单失败，均保留原库存。
- 持有活动锁时取消等待请求，数据库没有库存或订单变更；等待期间越过结束时间后返回 `activity_ended`。
- 真实 Redis Session 与 MySQL HTTP 链路验证成功购买、重复拒绝、本人订单查询、其他用户 404 与注销后的 401。
- 精确开始/结束边界、提交失败不能返回成功、身份及分页校验由单元测试覆盖；完整 Race 与实际服务联调记录见 [测试说明](../testing.md)。

## V2 增量：Redis 原子受理（内部组件）

已实现内部 `cache.Seckill` 的 `Prepare / Reserve / Receipt`，尚未接入 HTTP，也没有消费者落库。当前线上入口仍使用上述 V1 事务；不能把此组件通过测试视为 V2 已交付。

每张券使用同一 hash tag 下的 `locallife:seckill:{voucher_id}:state` 和 `:events`。状态 Hash 保存版本、32 位十六进制 generation、初始容量、剩余库存、开始/结束毫秒与 `buyer:<user_id>` → Stream ID 标记。初始化只允许两个 key 均不存在，创建 `orders` Consumer Group，读取位置从 `0-0` 开始；任何已有或残缺状态都返回冲突，不重置库存。

`Reserve` 在一次 Lua 执行中检查状态类型和数据、读取 Redis TIME、校验 `[begin,end)`、检查购买标记与库存，然后 XADD 并写回库存和标记。顺序先保证事件可投递，再扣减暂态库存。业务 ID 始终作为十进制字符串传递，支持完整 uint64；库存和毫秒时间限制在 Lua 可精确表示的非负整数范围内。

Redis 脚本的原子执行保证不被其他命令交叉执行，不代表发生运行错误时自动回滚。因此在写入前检查类型、数值和所需 ACL；XADD 报错不改变库存，后续 HSET 报错时清理本次事件。初始化 HSET 报错时清理新建空 Stream。异常清理仍依赖 Redis 可用及相关命令权限，不能把这套处理解释为跨系统事务或灾难下零丢失保证。依据见 [Redis Lua API](https://redis.io/docs/latest/develop/interact/programmability/lua-api/) 与 [Redis 原子操作和回滚说明](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)。

`Receipt` 原子读取购买标记与对应事件，检查用户、券与 generation，供未来接口在响应丢失后查询已受理凭据。它不返回订单已创建；最终结果必须查询 MySQL。缺失事件、错配或损坏记录报告依赖失败，不把不确定状态当作不存在。

状态和 Stream 当前不设 TTL、不自动裁剪，避免清理尚未落库的受理记录；后续退役清理必须结合已确认的最终结果和消费者状态。重复拒绝不会新增事件或再次扣库存；只有活动结束前受理的时间用于未来消费者资格核验，消费发生在结束后不应据此拒绝此前有效受理。

### 后续接入的必要条件

- 在 MySQL 持久化 generation 与异步模式，并在活动行锁下阻止同步/异步混写，再从受控快照初始化 Redis。不能仅调用 Prepare 后继续允许 V1 扣同一库存。
- 初始化是 create-only 原语，不是 Redis 数据丢失后的恢复命令。即使两个 key 都已丢失，也不能直接拿旧库存快照重新开放受理；需要暂停入口、核对 MySQL 与遗留消息，并走专用恢复流程。
- 消费者事务持久化最终结果与订单，支持按受理事件幂等；确认后 ACK，故障重试、Pending 接管、失败记录与补偿不能省略。
- 对外区分已受理与最终落库，提供归属当前用户的状态查询；Redis 故障或响应丢失后的不确定受理不能盲目补库存。
- 接入指标、退出取消/排空、持久化与丢失边界说明，再用同口径负载对照验证受理和最终订单。

内部组件的并发、故障与 Lua Benchmark 记录见 [测试说明](../testing.md) 和 [秒杀性能记录](../performance/seckill.md#lua-受理路径基线)。
